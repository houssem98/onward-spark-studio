## Status words

From `BankIntelli_Elite_Premium_Design_Roadmap.md#Classify every feature as implemented, partial, mocked, broken,`. Rules used here:

- implemented: does what it claims, and a named test proves it. Today no row qualifies.
- partial: works inside one browser session (in-memory store, client-written audit event) but is not persisted, permissioned or attributable to a real user (`src/repo/demo.ts#let state: State = {`, `src/repo/demo.ts#const USER = { name: "Sarah Mitchell", role: "Chief Risk Officer" };`).
- mocked: shows synthetic fixture data, or looks live and changes nothing or invents content.
- broken: does not work as presented.
- absent: linked or planned, no code. A placeholder that says the feature is not built counts as absent.
- not verified: code exists and was not judged.

A route row rates the data the page shows; its controls and exports have their own rows.

## Exports

Since L3 T5 every export asks the server before it downloads (`src/repo/export.ts#export async function exportFile(`): in production the database checks the role and writes an audit event, refusals included, and only executive, reviewer, model validator and admin may export; the demo adapter records the event and allows it (`src/repo/demo.ts#module: "Export"`). The file itself is still built in the browser from data the user could already read (`src/lib/calc.ts#export function downloadFile(`). So the export check governs the app's export buttons only. Any role can read its org's records straight from the data API, as CSV too, without asking the server and without an event; the L3 T8 council reproduced this as a credit analyst. A database cannot tell an export from a read, so holding data back from a role means not letting that role read it.
